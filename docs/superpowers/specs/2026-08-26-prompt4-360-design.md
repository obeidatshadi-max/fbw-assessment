- **Rater item format:** simplified 3-point Likert (Rarely/Sometimes/Often),
  3 items per dimension × 4 dimensions (F/B/W/Compliance-courage) = 12
  items, reusing the exact scale + UI pattern already used for `ORG_ITEMS`.
  Not the full 15-scenario forced-choice reworded to third person — too

  separate third-person rewrites.
- **Rater access:** public link with an embedded unguessable token
  (`/rate/<uuid>`), no login, no manual code entry.

## Schema (new migration `supabase/migrations/0002_fbw_360.sql`, applied to
the shared project)
Catches up two columns the original `0001_init.sql` never got after
Prompts 2/3 (it was written before those existed and never applied to any
live DB), then adds the 360 tables:

```sql
create table fbw_profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  created_at timestamptz not null default now()
);

create table fbw_assessments (
  id uuid primary key default gen_random_uuid(),
  profile_id uuid references fbw_profiles(id) on delete cascade,
  completed_at timestamptz not null default now(),
  role text,
  scenario_answers jsonb not null,
  org_answers jsonb not null,
  compliance_answers jsonb,
  scores jsonb not null
);

create table fbw_rater_links (
  id uuid primary key default gen_random_uuid(),
  assessment_id uuid references fbw_assessments(id) on delete cascade,
  leader_profile_id uuid references fbw_profiles(id) on delete cascade,
  created_at timestamptz not null default now(),
  min_raters int not null default 3,
  closed_at timestamptz
);

create table fbw_rater_responses (
  id uuid primary key default gen_random_uuid(),
  rater_link_id uuid references fbw_rater_links(id) on delete cascade,
  submitted_at timestamptz not null default now(),
  dimension_scores jsonb not null -- {F,B,W,C} raw 3–9 sums, no identity fields
);
```

RLS:
- `fbw_profiles` / `fbw_assessments`: same own-row policies as `0001_init.sql`
  (`auth.uid() = id` / `auth.uid() = profile_id`), just renamed.
- `fbw_rater_links`: leader can `insert`/`select` where
  `leader_profile_id = auth.uid()`. `anon` + `authenticated` get a narrow
  `select` (id, closed_at only needed to validate the link client-side) —
  no PII on this table (leader_profile_id is a bare uuid), so this is safe.
- `fbw_rater_responses`: `anon` + `authenticated` get `insert` only, gated
  by `exists (select 1 from fbw_rater_links l where l.id = rater_link_id
  and l.closed_at is null)`. **No `select` policy at all** — nobody, not
  even the leader, can read raw rows directly. This is what makes rater
  anonymity structural rather than a UI convention.
- `get_360_summary(link_id uuid)` — `security definer` RPC. Verifies
  `auth.uid()` owns the link, counts responses, returns `{count, scores:
  null}` if `count < min_raters`, else `{count, scores: {F,B,W,C}}`
  (per-dimension averages). This is the **only** way to read aggregated
  rater data, and it enforces the minimum-rater gate server-side — not
  just a client check that a modified frontend could bypass.

## Scoring / normalization
Self scores are ipsative (forced-choice `most` counts, sum to 15 across
F/B/W; compliance is a separate 3–9 scale). Rater scores are a Likert sum
per dimension (3–9 each). These are different scale types, so direct
number-to-number comparison would be misleading. Both sides are converted
to **relative profile-shape percentages** before comparing:
- Self: `pct_k = most[k] / 15 * 100` for F/B/W (already how the report
  displays them); compliance self pct reuses the existing
  `(score-3)/6*100` clamp already in `scoring.js`.
- Rater: average each dimension's 3–9 sum across all responses, then
  `pct_k = avg_k / sum(avg_F, avg_B, avg_W, avg_C) * 100`.
- Gap per dimension = `raterPct - selfPct`. Positive = others rate it
  higher than the leader does (hidden strength); negative = blind spot.

This is documented as an approximation in the report copy, consistent with
the existing disclaimer that this is not a validated psychometric
instrument and scores are self-relative, not absolute.

## Known limitation (documented, not silently hidden)
No rater identity exists, so nothing stops one person submitting more than
once. Acceptable for v1 (matches the "anonymous, low-friction" goal); would
need a per-rater one-time sub-token (emailed individually) to close, which
is out of scope here — noted in `CLAUDE.md` as a future hardening item if
this becomes higher-stakes (e.g. talent review, Prompt 8).
